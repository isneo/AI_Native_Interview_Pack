3. 概念、组件与业务映射

同一套 AI Native 技术词，在客服和风控里对应的是不同业务资产。面试时要先讲业务语义，再讲技术实现。

客服领域Customer Ticket Agent
  • 核心产物客服回复建议
  • 知识资产FAQ、产品政策、售后规则、话术规范
  • 上下文工单、客户画像、订单、历史沟通
  • 工具查询工单、客户、订单、退款审批
  • 流程检索知识 -> 查业务数据 -> 生成回复
  • 反馈采纳、修改、拒绝、语气或政策问题
  • 指标回复准确率、采纳率、处理时长、满意度
风控领域Risk Review Agent
  • 核心产物证据链、风险判断、处置建议、转人工理由
  • 知识资产审核规则、风控策略、SOP、案例库、申诉规则
  • 上下文行为日志、交易、设备/IP、历史处罚、规则命中
  • 工具查日志、查图谱、查黑名单、查相似案例、查处置记录
  • 流程案件理解 -> 证据查证 -> 规则对齐 -> 风险评级 -> 建议处置
  • 反馈人工复核、质检、申诉、误杀漏放、新风险样本
  • 指标误杀率、漏放率、规则引用准确率、证据完整率

4. 五大主线 × 三大支柱

五大主线不是五个独立 Agent，而是统一 Risk Review Orchestrator 下面的五类能力模块；三大支柱是所有模块共享的底座。

支柱 1

审核域知识治理

规则、策略、SOP、案例、反例库、质检标准、申诉规则和专家经验，负责让 Agent 有依据、有边界、有版本。

支柱 2

案件上下文与证据工具

用户行为、交易、日志、设备/IP、图谱关系、历史处罚和工具查证结果，负责让 Agent 有证据。

支柱 3

Harness 约束与治理

权限边界、流程边界、动作边界、人工复核、审批、审计和灰度回滚，负责让 Agent 受控运行。

统一编排器Risk Review Orchestrator 负责一次案件的上下文、证据链、规则版本和 Trace 连续性。
1 风险发现与识别从行为和规则命中中识别风险信号、新风险模式和待查证证据。
2 审核研判与决策聚合证据、对齐规则、判断风险等级、输出置信度和审核建议。
3 案件流转与处置编排决定自动通过、补证据、转人工、升级复核或生成处置草案。
4 知识沉淀与治理把复核、质检、申诉和误判案例沉淀成候选规则、案例和反例。
5 受控反馈与体系进化做问题归因、生成更新候选、灰度验证、监控效果并可回滚。

主链路

一个统一 Orchestrator

风险发现、审核研判、处置流转属于一次案件的同步主路径，必须共享上下文、证据链、规则版本和连续 Trace，所以放在一个统一编排器里更稳。

治理链路

后处理可异步拆分

知识沉淀和体系进化是复核、质检、申诉之后的治理任务，可以拆成 Worker 或 Sub-Agent，但只能生成候选更新，不能直接改线上规则。

6. 面试表达

推荐用“先跑通通用骨架，再迁移到风控领域”的方式讲，避免被认为只是把客服 Demo 换了个名字。

我没有一开始直接堆一个复杂的自主 Agent，而是先用客服工单场景跑通 AI Native Agent 的通用工程骨架，包括 AgentRun、Trace、Tool Governance、HITL、Eval、Feedback、Iteration 和 MCP 工具接入。

这套骨架的价值在于，它把一次 AI 任务从“模型生成答案”升级成了“可执行、可观测、可评估、可反馈、可迭代”的产品闭环。

如果迁移到风控审核领域，我不会推倒重来，而是保留平台层能力，把领域层从 Ticket Assist 替换成 Risk Review：知识资产从 FAQ 变成审核规则、SOP 和案例库；上下文从工单和订单变成用户行为、日志、交易、设备关系和历史处罚；工具从查询工单变成查证据、查图谱、查相似案例和查处置记录；输出从客服回复变成证据链、风险判断、处置建议和转人工理由。

在架构表达上，我会把风控审核拆成五大主线：风险发现与识别、审核研判与决策、案件流转与处置编排、知识沉淀与治理、受控反馈与体系进化。但我不会把它们默认设计成五个彼此独立的 Agent。风控审核是强流程、强审计、强责任边界的场景，一次案件需要共享同一个上下文、证据链、规则版本和 Trace，所以主链路更适合采用一个统一的 Risk Review Orchestrator 来编排。

前三条主线属于同步审核主链路，放在统一 Orchestrator 内部以 Workflow / Skill 的方式执行；后两条偏异步治理，可以拆成 Worker 或 Sub-Agent，用于生成知识候选、归因反馈、构建评测样本和提出灰度更新方案。

三大支柱是所有主线共享的底座：审核域知识治理解决规则、SOP、案例和申诉规则如何被 Agent 使用和更新；案件上下文与证据工具解决一次审核里 Agent 看什么证据、调什么工具；Harness 约束与治理解决 Agent 能做什么、不能做什么、什么时候必须转人工。

真正需要重做的是风控领域建模、证据链、审核策略、Harness 边界和评测指标。也就是说，这不是客服系统换皮，而是用同一套 AI Native 平台骨架承载一个更高风险、更强调审计和治理的风控审核业务域。
