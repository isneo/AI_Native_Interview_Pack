Production Risk Architecture Boundary

Agent 不替代高性能规则引擎，而是增强复杂审核、解释和体系进化。

真实风控系统的高并发、低延时主链路应由规则引擎、特征服务和模型打分承担；风控审核 Agent 位于实时决策之后，处理灰区案件、高影响处置、申诉复核、证据解释和策略归因。

关键修正

前面的叙事少了“实时规则引擎是第一道防线”这个生产边界。

这个点会影响整体架构表达：项目不应讲成“Agent 承接所有风控请求”，而应讲成“规则引擎负责毫秒级实时决策，Agent 负责复杂案件审核和反馈进化”。

2. 规则引擎和 Agent 的定位

这两个系统解决的问题不同。生产级风控不能让 LLM Agent 进入所有毫秒级在线请求主链路。

4. 高并发、低延时设计

高性能靠实时决策层，Agent 靠分流、队列、Worker 池和成本预算。不要把大模型调用放进所有交易/登录同步路径。

实时层

毫秒级主链路

规则预编译、特征缓存、短路执行、模型超时降级、规则版本绑定和命中日志，保证实时请求可控。

队列层

异步削峰

灰区和高影响案件进入 Kafka / Pulsar / Redis Stream 等队列，按风险等级、SLA 和人工队列做优先级调度。

Agent 层

预算化执行

Agent Worker 池控制并发、超时、最大工具步数、模型成本和失败降级；高风险动作必须经 Harness 和人工审批。

6. 面试表达

这段适合回答“高并发怎么办”“规则引擎和 Agent 什么关系”“Agent 是不是替代规则引擎”。

我不会把风控审核 Agent 放在全量实时风控主链路上承接所有请求。高并发、低延时的登录、交易、内容发布等场景，第一道防线仍然是特征服务、规则引擎和模型打分服务，它们负责毫秒级判断，输出放行、拦截、二次验证或进入审核队列。

Agent 的位置在规则引擎之后，主要处理灰区案件、高影响处置前复核、申诉复核、复杂证据解释和策略归因。规则引擎负责快和稳，Agent 负责复杂研判、可解释和体系进化。

两者通过 RiskCase、Evidence Snapshot、Rule Version 和 Feedback Loop 连接。规则引擎命中后，如果是灰区或高影响场景，会生成审核案件并固化当时的特征、规则命中、模型分和证据快照；Agent 基于这些证据、规则、SOP、历史案例和工具查证结果输出审核建议；人工复核、质检和申诉结果再沉淀为规则候选、案例库、评测集和模型样本，经过灰度验证后反哺规则引擎。

所以这个系统不是用 Agent 替代高性能规则引擎，而是用 Agent 增强规则引擎的解释、复核和进化能力。这个定位也会影响架构叙事：总架构应该从“实时决策层 -> 案件审核层 -> 反馈进化层”三层讲，而不是只讲 Agent 内部五条主线。
