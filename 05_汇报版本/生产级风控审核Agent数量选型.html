Risk Review Agent System · Production Architecture

真实生产系统不建议一开始做 5 个平级 Agent。

最稳妥的设计是：一个主审核 Orchestrator 负责同步案件链路，2-3 个异步治理 Agent / Worker 负责知识沉淀、评测回归和策略进化。这样既保留 AI Native 的模块化能力，又避免多 Agent 带来的证据割裂、责任不清和治理成本失控。

推荐结论

生产级建议采用“1 个主 Agent + 3 个治理 Agent/Worker”的混合架构。

主链路保持统一编排：风险识别、审核研判、处置流转在同一个案件上下文和证据链里完成。治理链路异步拆分：知识治理、评测回归、策略进化独立运行，只生成候选更新，不直接改线上规则。

3. 为什么不是 5 个平级 Agent

五条主线是业务生命周期，不等于必须拆成五个运行时 Agent。生产系统里更重要的是证据链一致、审计连续、责任可归因。

风险 1

证据链割裂

风险识别 Agent、决策 Agent、流转 Agent 如果各自维护上下文，容易出现证据遗漏、规则版本不一致和结论不一致。

风险 2

事故归因困难

一旦误杀或漏放，难以判断问题来自风险识别、证据查证、规则引用、流转策略还是 Agent 间通信。

风险 3

治理成本倍增

每个 Agent 都要做权限、审计、评测、灰度、回滚、监控和提示词版本，生产复杂度会快速上升。

风险发现与识别 主 Orchestrator 内的 Capability / Workflow 必须和后续研判共享案件上下文和证据快照 可，但不优先
审核研判与决策 主 Orchestrator 核心能力 它是最终审核建议的责任主体，不能拆散责任边界 不建议拆

4. 演进路线

从工程落地角度，不建议一步到位多 Agent。先用统一主链路跑通证据、Trace、HITL、Eval，再把后处理治理能力逐步拆出去。

阶段 1

单 Orchestrator

先把风险识别、审核研判、处置流转、Trace、证据链、人工复核跑通。目标是可审计、可复核、可评测。

阶段 2

拆异步治理 Agent

把知识沉淀、评测回归、反馈归因拆成异步 Worker。目标是让主链路稳定，治理链路可扩展。

阶段 3

选择性 Agent 化

当某类风险、某类处置或某类评测足够复杂，再拆垂直专用 Agent，如交易风险 Agent、内容风险 Agent。

5. 面试表达

可以直接复制这段回答。重点是说明：五条主线是业务能力拆分，不等于运行时必须五个 Agent。

如果是真实生产级风控审核系统，我不会一开始把五条主线设计成五个平级 Agent。风控审核是强流程、强审计、强责任边界的场景，一次案件必须共享同一个上下文、证据链、规则版本和 Trace，所以主审核链路更适合由一个 Risk Review Orchestrator 统一编排。

我的推荐架构是“1 个主 Agent + 3 个异步治理 Agent/Worker”。主 Agent 负责同步链路：风险发现与识别、审核研判与决策、案件流转与处置编排。它对一次审核建议负责，并通过 Harness 控制工具权限、动作边界、人工复核和高风险审批。

后处理链路可以拆成三个异步治理 Agent：Knowledge Governance Agent 负责从复核、质检、申诉中生成规则和案例候选；Eval Regression Agent 负责评测集构建、版本回放和失败归因；Policy Evolution Agent 负责影响面分析、灰度建议、监控指标和回滚方案。它们只能生成候选更新，不能直接改线上规则。

这样设计的好处是，主链路保持一致性和可审计性，治理链路保持可扩展性和可演进性。五条主线仍然完整覆盖，但不是机械拆成五个 Agent，而是按同步主链路和异步治理链路做架构分层。
