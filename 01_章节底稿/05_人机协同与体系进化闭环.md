# 第 3B 章｜人机协同与体系进化闭环

## 本章定位

本章讲运行闭环的后半段：**系统如何从一次次审核、人工复核、质检、申诉和新风险样本中持续进化。**

这里使用“体系进化”而不是“全自动自进化”，是为了强调：风控审核是高风险场景，进化必须受控、可评审、可灰度、可回滚。

## 核心链路

```text
Agent 审核输出
  ↓
人工复核 / 质检 / 申诉 / 复盘
  ↓
反馈信号采集
  ↓
问题归因
  ↓
候选更新生成
  ↓
人工审核 / 灰度验证 / 效果监控
  ↓
体系更新
  ↓
下一轮 Agent 审核能力提升
```

## 反馈来源

```text
人工复核结果
质检结果
申诉结果
策略复盘
新风险样本
线上误判 / 漏判案例
审核员反馈
工具调用失败记录
规则冲突记录
```

## 反馈信号是什么

反馈不是简单的“对 / 错”标签，而是能推动体系进化的结构化信号：

```text
原判断是什么
人工修正了什么
修正理由是什么
缺了哪类证据
规则引用是否准确
是否存在规则冲突
是否应转人工但没有转
处置动作是否过重或过轻
申诉是否推翻原判定
```

## 反馈归因

每个反馈不应该只被看成一个错误样本，而要归因到体系中的不同位置：

```text
知识缺口：
规则、案例、SOP、处置标准不足。

上下文缺口：
缺少关键行为数据、日志、图谱关系或证据信息。

工具缺口：
现有工具无法提供关键证据，或工具调用失败。

Harness 边界缺口：
自动化边界、人工复核边界、动作边界定义不清。

流程缺口：
案件流转、人机协同或处置编排不合理。

评估缺口：
离线评估集没有覆盖该类风险或边界场景。
```

## 体系更新

归因之后，反馈可以进入不同更新路径：

```text
审核域知识治理更新：
规则、SOP、案例、反例库、质检标准、申诉规则。

案件上下文与证据工具更新：
新增证据字段、工具能力、图谱关系、日志查询方式。

Harness 约束与治理更新：
工具权限、动作边界、转人工条件、风险门控。

Agent 化审核链路更新：
Prompt、Workflow、任务拆解方式、输出结构。

评估体系更新：
离线评估集、回归测试集、线上监控指标。
```

## 受控进化原则

```text
Agent 可以生成候选更新，但不能无约束发布。
高影响规则和处置边界必须人工审核。
上线前需要灰度验证和效果监控。
所有版本必须可追溯、可回滚。
越靠近自治，越需要保守。
```

## 和五条主线的关系

```text
知识沉淀与治理：
负责把复核、质检、申诉和新风险样本结构化。

受控反馈与体系进化：
负责把结构化反馈变成可评审、可验证、可回滚的体系更新。
```

## 一句话总结

Agent 每次审核不只是完成任务，也是在验证体系。人机反馈不只是纠错，而是在推动审核域知识、案件上下文、工具能力、Harness 边界、审核流程和评估体系持续进化。
