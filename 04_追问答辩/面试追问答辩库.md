# 面试追问答辩库

## 使用方式

这份答辩库按四类组织：

```text
方向类：回答项目为什么是 AI Native
架构类：回答五条主线、三大支柱和运行闭环
技术类：回答 RAG、Tool、Harness、Eval 等实现问题
压力类：回答幻觉、误判、规则冲突、体系进化污染和个人贡献
```

## 一、方向类追问

### 1. 为什么这个项目叫 AI Native？

因为它不是简单把大模型接入审核页面，而是把风控审核业务域中的知识、流程、工具、权限、证据和反馈机制，围绕 Agent 重新设计。

AI Native 体现在：知识可被 Agent 消费，案件上下文可被 Agent 组装，工具可被 Agent 受控调用，权限和动作边界通过 Harness 约束，输出结果可解释，人工复核、质检和申诉反馈能反哺体系迭代。

### 2. 和普通 RAG / Copilot 有什么区别？

普通 RAG 或 Copilot 更像是问答和辅助查询；这个项目关注的是完整风控审核业务域的 Agent 化。

RAG 只是审核域知识治理的一种实现方式，真正核心是 Agent 如何在案件上下文与证据工具、业务工具和 Harness 约束下完成风险研判，并通过人工复核、质检、申诉和新风险样本推动体系进化。

### 3. 为什么不是单点审核助手？

因为项目改造对象不是一个页面或一个问答入口，而是整个审核业务链路。它覆盖风险发现与识别、审核研判与决策、案件流转与处置编排、知识沉淀与治理、受控反馈与体系进化五条主线。

单点助手解决的是“人怎么更快查信息”，这个项目解决的是“风控审核体系如何被 Agent 驱动、约束、解释和进化”。

### 4. AI+ 和 AI Native 到底有什么区别？

AI+ 是在既有流程上叠加 AI 能力，比如加一个审核问答助手、摘要工具或推荐入口。AI Native 是以模型和 Agent 能力为前提，重新设计业务流程、交付物、人机边界和反馈闭环。

本质区别是：

```text
AI+ 是能力叠加。
AI Native 是生产关系重构。
```

在风控审核里，AI+ 更像“帮审核员查资料”；AI Native 是把风险发现、证据组装、规则对齐、审核研判、案件流转、人工复核和反馈进化重构成 Agent 可执行、可约束、可解释、可评估、可进化的体系。

### 5. AI Native 里人还做什么？

人不是被替代，而是从重复查证和经验拼接，转向目标定义、风险裁决和体系治理。

Agent 负责组装上下文、调用工具、聚合证据、对齐规则、生成审核 artifact；人负责定义目标和边界，确认高风险、低置信、规则冲突和高影响处置，并把复核、质检、申诉结果转成反馈信号。

人的输入是审核目标、业务约束、复核意见和纠错原因；人的输出是最终裁决、处置动作、反馈标注、知识更新审核和边界调整。

### 6. Agent 最后交付什么？

Agent 不应该只交付一句自然语言结论，而要交付可审计的审核 artifact。

核心 artifact 包括：

```text
风险类型
证据链
规则依据
建议动作
置信度与风险等级
待人工确认项
执行 trace
反馈入口
```

人可以基于 artifact 做最终裁决，系统可以基于 trace 和反馈做评测、归因和后续迭代。

## 二、架构类追问

### 7. 五条主线为什么这么拆？

因为风控审核不是单次模型判断，而是一条完整业务链路。

```text
风险发现与识别：发现风险线索
审核研判与决策：判断风险性质和证据充分性
案件流转与处置编排：决定怎么分流、复核和处置
知识沉淀与治理：把经验、案例和反馈结构化
受控反馈与体系进化：把反馈转化为可评审、可验证、可回滚的体系更新
```

这五条主线覆盖了风险事件从发现、判断、处置，到沉淀和反哺的完整生命周期。

### 8. 三大支柱分别解决什么问题？

三大支柱是所有主线共享的能力底座：

```text
审核域知识治理：
解决规则、SOP、案例、质检标准和申诉规则如何被 Agent 消费和迭代。

案件上下文与证据工具：
解决一次 one-off 审核任务里，Agent 这次看什么、查什么、引用什么。

Harness 约束与治理：
解决 Agent 在什么权限、流程、动作和人工复核边界内运行。
```

### 9. 执行闭环和领域架构母图是什么关系？

领域架构母图回答“业务域怎么拆、能力怎么复用”；执行闭环回答“系统具体怎么跑”。

```text
五条主线 × 三大支柱 = 领域架构
知识资产 → 上下文 → Agent → Harness → 证据链 → 人工反馈 → 体系更新 = 运行路径
```

## 三、技术类追问

### 10. Agent 会不会幻觉，怎么控制？

风控审核不能让模型凭感觉判断，所以我们采用证据驱动。事实必须来自工具、规则、日志、案例或知识资产；模型主要负责信息整合、证据组织和解释生成。

输出中要区分已验证事实、模型推断和待人工确认项。高风险、低置信、规则冲突或高影响处置必须进入人工复核。

### 11. Harness 到底是什么？

在这个项目里，Harness 不是独立安全沙箱，而是审核域对 Agent 的权限边界、流程边界、动作边界和人工复核边界。

它定义 Agent 在什么场景下可以调用什么工具，哪些数据可以读取，哪些结论只能建议不能执行，哪些案件必须转人工复核，哪些高影响处置必须留痕和复核。

### 12. 为什么风控上下文不是对话历史？

风控审核通常是 one-off 的案件处理任务。Agent 处理的是一个具体案件，不是多轮闲聊。

因此重点不是长期对话记忆，而是案件级上下文组装，包括用户历史行为、当前触发规则、操作日志、设备关系、历史处罚、相似案例、内容上下文和工具查证结果。

### 13. 规则引擎和 Agent 的关系是什么？

规则引擎适合处理明确、稳定、可结构化的强规则；Agent 适合处理多源信息整合、语义理解、案例类比、证据解释和复杂边界判断。

二者不是替代关系，而是协同关系：强规则走规则引擎，复杂判断由 Agent 辅助，模糊、高风险或低置信场景进入人工复核。

## 四、压力类追问

### 14. 受控反馈与体系进化会不会污染知识体系？

不会让反馈直接写入知识体系。反馈要先经过归因、候选生成、冲突检测、适用范围判断、人工审核、灰度验证、效果监控和版本回滚机制。

Agent 可以生成候选知识或候选策略，但不能无约束发布。越靠近自治，越需要保守。

### 15. 如果模型判断和规则冲突，怎么办？

强规则优先，模型不能覆盖强规则。

Agent 可以指出冲突、补充证据、解释原因或建议人工复核，但不能绕过规则直接执行高影响动作。规则冲突本身也会作为反馈信号进入知识治理和 Harness 边界更新。

### 16. 如何评估 Agent 的效果？

不能只看模型回答质量，而要看业务指标、质量指标和体系指标。

```text
业务效率：
审核耗时、查证步骤、证据链生成耗时、低风险分流比例。

审核质量：
人工采纳率、证据链完整率、规则引用准确率、误判率、漏判率、申诉修正率。

体系进化：
反馈归因完成率、知识更新覆盖率、评估集新增覆盖率、工具调用成功率、Harness 边界更新记录。
```

### 17. 数据飞轮怎么形成？

数据飞轮不是把线上数据无脑喂回模型，而是把每次执行、复核和失败都转化为可治理资产。

```text
Agent 执行
→ 产生 artifact 和 trace
→ 人工复核 / 质检 / 申诉
→ 形成结构化反馈
→ 归因到知识、上下文、工具、Harness、流程或评测问题
→ 生成候选更新
→ 人工审核和灰度验证
→ 更新知识库、工具能力、Prompt / Workflow、Harness 边界和评测集
→ 下一轮审核质量提升
```

关键是反馈先归因，再更新；候选先审核，再发布；上线先灰度，再扩大；所有变更可追溯、可评估、可回滚。

### 18. 你个人贡献可以怎么讲？

可以按三层讲：

```text
第一，方向和架构：
参与 / 负责风控审核业务域 AI Native Agent 化的叙事、目标态和领域架构设计。

第二，关键链路：
参与 / 负责审核域知识治理、案件上下文与证据工具、Agent 化审核链路、Harness 约束或证据链输出中的关键模块。

第三，闭环和验证：
推动人工复核、质检、申诉和新风险样本进入反馈归因与体系更新，并用指标验证提效、提质和进化价值。
```
